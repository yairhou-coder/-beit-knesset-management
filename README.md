## הפעלה מהירה

דרוש **Node.js 22 ומעלה** ([nodejs.org](https://nodejs.org) — גרסת LTS).

> בהתקנת Node בחלונות מוצגת בסוף אפשרות להתקין *Tools for Native Modules*
> (Chocolatey, Python ו-Visual Studio Build Tools, כ-7 ג'יגה). **אין בה צורך.**
>
> ההתקנה מתבצעת עם `--ignore-scripts`. הרכיב המקומפל היחיד בפרויקט,
> `better-sqlite3`, מגיע עם בינארי מוכן לכל מערכת הפעלה בתוך החבילה עצמה.
> ללא הדגל הזה npm בחלונות מנסה להריץ `node-gyp` ונכשל אצל מי שאין לו
> Visual Studio - גם כאשר החבילה עצמה מסומנת כמי שאינה זקוקה לבנייה.

```bash
# שימו לב: שם המאגר מתחיל במקף, ולכן משכפלים לתיקייה בשם רגיל
git clone https://github.com/yairhou-coder/-beit-knesset-management.git beit-knesset
cd beit-knesset

npm run setup    # מתקין את התלויות ויוצר נתוני דוגמה
npm run dev      # http://localhost:3000
```

הכתובת נפתחת בדפדפן: **http://localhost:3000**

## הפעלה בלחיצה אחת (אייקון בשולחן העבודה)

במקום להריץ פקודות בכל פעם, אפשר ליצור אייקון בשולחן העבודה שמפעיל את
המערכת ופותח את הדפדפן לבד.

המפעיל (`scripts/launch.mjs`) עושה הכול בעצמו: מתקין תלויות אם חסרות,
יוצר בסיס נתונים בהרצה הראשונה, בוחר פורט פנוי אם 3000 תפוס, מריץ את
השרת ופותח את הדפדפן ברגע שהמערכת מוכנה.

### חלונות

הדרך הקצרה — פקודה אחת ב-PowerShell מתוך תיקיית הפרויקט:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\create-shortcut.ps1
```

הסקריפט יוצר קיצור דרך בשולחן העבודה בשם **בית המדרש אנשי מעשה**, עם הלוגו
כסמל. הוא מזהה גם שולחן עבודה שמופנה ל-OneDrive.

לחלופין, ידנית:

1. לחיצה ימנית על `start-windows.cmd` ← **שלח אל** ← **שולחן העבודה (יצירת קיצור דרך)**.
2. לחיצה ימנית על הקיצור ← **מאפיינים** ← **שנה סמל** ← **עיון**,
   ובחירת `src\web\assets\anshei-maase.ico`.

### macOS

1. לחיצה כפולה על `start-mac.command`. בפעם הראשונה ייתכן שתידרש לחיצה ימנית ← **Open**
   כדי לאשר את ההרצה.
2. גרירת הקובץ לשולחן העבודה בלחיצה על `Cmd`+`Option` (יוצרת קיצור דרך).
3. להחלפת הסמל: `Cmd`+`I` על הקובץ, וגרירת `src/web/assets/logo-mark.png` אל הסמל הקטן שבפינה.

### לינוקס

`start-linux.sh` — יש לסמן אותו כניתן להרצה בקובץ המנהל, או ליצור קובץ `.desktop`
שמצביע עליו.

**עדכונים:** בכל הפעלה המפעיל מושך את הגרסה האחרונה מהמאגר, כך שאין צורך
להריץ `git pull` ידנית. הוא מדלג על כך אם יש שינויים מקומיים בתיקייה,
וכשל בעדכון לעולם אינו מונע את ההפעלה.

**ייבוא בלי טרמינל:** לחיצה כפולה על `import-data.cmd` מעדכנת ומייבאת את
חברי הקהילה. לאחר מכן יש לרענן את הדפדפן ב-`Ctrl+F5`.

**לתשומת לב:** חלון הטרמינל שנפתח הוא המערכת עצמה — סגירתו עוצרת אותה.
אפשר למזער אותו. הנתונים נשמרים בקובץ `data/beit-knesset.db` ואינם נמחקים
בין הפעלות.

הפעלה ראשונה אורכת כדקה (התקנה); כל הפעלה לאחר מכן — כשתי שניות.

לעצירת השרת: `Ctrl+C`. להפעלה חוזרת: `npm run dev` בלבד — הנתונים נשמרים
בקובץ `data/beit-knesset.db` ואינם נמחקים.

אם פורט 3000 תפוס: `PORT=3100 npm run dev` (בחלונות: `set PORT=3100 && npm run dev`).

פקודות נוספות:

| פקודה | תיאור |
| --- | --- |
| `npm run setup` | התקנה ראשונית: תלויות + נתוני דוגמה |
| `npm run launch` | הפעלה בלחיצה אחת (מה שהאייקון בשולחן העבודה מריץ) |
| `npm run import -- --reset` | ייבוא חברי הקהילה מקובץ האקסל |
| `npm test` | הרצת כל הטסטים (87 טסטים) |
| `npm run typecheck` | בדיקת טיפוסים |
| `npm run build` | קומפילציה ל-`dist/` |
| `npm start` | הרצת הגרסה המקומפלת |

## עקרונות הליבה

### 1. התחייבות איננה הכנסה

זהו העיקרון המרכזי של המערכת. ארבע ישויות **נפרדות**, כל אחת בטבלה משלה:

| ישות | טבלה | משמעות |
| --- | --- | --- |
| **Commitment** | `commitments` | חוב שנוצר. **אינו** הכנסה. |
| **Payment** | `payments` | כסף שהתקבל בפועל. |
| **Income** | `incomes` | הכנסה — נרשמת **רק** כשמתקבל תשלום. |
| **Receipt** | `receipts` | מסמך שהופק מול ספק חיצוני. |

בזכות ההפרדה, הדוחות מבדילים בין **התחייבויות**, **כספים שנגבו בפועל** ו**יתרות שטרם נגבו**.

### 2. כל סכום נשמר באגורות שלמות

כל שדה כספי הוא `INTEGER` באגורות (`amount_agorot`). אין שימוש ב-`REAL` לכסף,
ולכן אין שגיאות עיגול. ההמרה לשקלים נעשית בשכבת התצוגה בלבד.

ה-API מקבל `amountAgorot` (מספר שלם) או `amountShekels` (לנוחות), ומחזיר תמיד אגורות.

### 3. הפרדה מוחלטת בין העמותות

לכל רשומה כספית — התחייבות, תשלום, הכנסה, קבלה, הוצאה, הוראת קבע — יש `organization_id`.
לכל עמותה הגדרות משלה: פרטי חשבון, ספקי סליקה/קבלות/הודעות, מפתחות API,
סוגי מסמכים מותרים ואופן הפקת קבלות. הדוחות מציגים כל עמותה בנפרד ובנוסף תמונה מאוחדת
— שהיא **סכימה** של העמותות, לא ערבוב שלהן.

## תהליך התשלום המלא

התרחיש מהאפיון, כפי שהמערכת מממשת אותו:

```
שלב 1  נוצרת התחייבות                    התחייב 1,800 · שולם 0     · יתרה 1,800 · פתוח
שלב 2  מתקבל תשלום 1,000 ₪                התחייב 1,800 · שולם 1,000 · יתרה 800   · שולם חלקית
       ├─ נרשמת הכנסה על 1,000 ₪
       └─ מופקת קבלה על 1,000 ₪
שלב 3  מתקבל תשלום 800 ₪                  התחייב 1,800 · שולם 1,800 · יתרה 0     · שולם במלואו
       ├─ נרשמת הכנסה נוספת על 800 ₪
       └─ מופקת קבלה נוספת
```

הכול דרך קריאה אחת: `POST /api/payments`.

**מה קורה מתחת לפני השטח** (`src/services/payments.ts`):

1. **בתוך טרנזקציה אחת:** נרשם התשלום → מחושבת מחדש יתרת ההתחייבות → נרשמת ההכנסה →
   נוצרת רשומת הקבלה בסטטוס "ממתין".
2. **אחרי ה-commit:** מתבצעת הקריאה לספק הקבלות.

הסדר הזה הוא מה שמבטיח שכשל אצל ספק חיצוני לעולם לא ימחק תשלום או הכנסה.

הסכום ששולם **מחושב מחדש** מסכום התשלומים שהושלמו (`recalculateCommitmentTotals`)
ולא מתעדכן בהפרשים, כך שגם זיכוי או תיקון מביאים ליתרה נכונה. עמודת היתרה
(`balance_agorot`) היא עמודה מחושבת ב-SQLite ואינה יכולה לצאת מסנכרון.

## טיפול בכשלים

אם ספק הקבלות אינו זמין:

| מה קורה | מה **לא** קורה |
| --- | --- |
| ✅ התשלום נשמר | ❌ התשלום אינו נמחק |
| ✅ ההכנסה נרשמת | ❌ ההכנסה אינה אובדת |
| ✅ הקבלה נשארת "ממתין להפקה" | ❌ אין קבלה כפולה |
| ✅ נוצרת התראה למנהל | |
| ✅ ניתן לנסות שוב, בודד או מרוכז | |

### מניעת קבלות כפולות — שלוש שכבות

1. **`payments.idempotency_key`** — `UNIQUE`. רישום חוזר של אותו תשלום מחזיר את
   הרשומה הקיימת ואינו יוצר תשלום, הכנסה או קבלה נוספים.
2. **`receipts(payment_id) WHERE status != 'cancelled'`** — אינדקס ייחודי חלקי.
   לתשלום יכולה להיות קבלה פעילה אחת בלבד; קבלה שבוטלה אינה חוסמת הפקת קבלה חלופית.
3. **`receipts.idempotency_key`** — נשלח לספק. הספק מחויב להחזיר את אותה קבלה
   עבור אותו מפתח. רשומת הקבלה נוצרת **לפני** הקריאה לספק, כך שגם אם התשובה
   אובדת בדרך — הניסיון הבא ישתמש באותו מפתח ולא ייווצר מסמך שני.

### קבלה אוטומטית או באישור ידני

נקבע **לכל עמותה בנפרד** (`organizations.receipt_issue_mode`):

- `automatic` — הקבלה מופקת מיד עם קבלת התשלום.
- `manual_approval` — הקבלה נשמרת בסטטוס "ממתין לאישור" עד לאישור גזבר/מנהל.
  ההכנסה נרשמת בכל מקרה.

## Integration Layer

הלוגיקה המרכזית מדברת אך ורק מול הממשקים שב-`src/integrations/types.ts`,
ולעולם לא מול ספק ספציפי.

```
ReceiptProvider       createReceipt · getReceipt · cancelReceipt
                      downloadReceipt · checkReceiptStatus

PaymentProvider       charge · getPaymentStatus · refund
                      createSubscription · getSubscriptionStatus · cancelSubscription
                      parseWebhook  (כולל אימות חתימה)

NotificationProvider  send  (WhatsApp / SMS / Email)
```

**חיבור ספק אמיתי** — מימוש הממשק ורישום ב-`src/integrations/registry.ts`:

```ts
receiptProviders.register('greeninvoice', (orgId, config) =>
  new GreenInvoiceProvider(config),
);
```

ואז בהגדרות העמותה: `receiptProvider: 'greeninvoice'` + `receiptConfig` עם פרטי ה-API.
**אין צורך לשנות שורה אחת בשירותים.**

בשלב זה משמשים **Mock Providers מלאים** המאפשרים בדיקה מקצה לקצה, כולל מסלולי כשל:
מספור קבלות רץ, יצירת PDF תקין, ביטול, בדיקת סטטוס, כרטיס שנדחה, פג תוקף כרטיס,
ו-Webhooks חתומים.

### Webhooks

`POST /api/organizations/:id/webhooks/payments`

הגוף הגולמי נשמר לצורך אימות החתימה. כל אירוע נרשם ב-`provider_webhook_events`,
ואירוע שכבר עובד אינו מעובד שוב. אירועים נתמכים: הצלחת/כשל תשלום, זיכוי,
סטטוס וביטול הוראת קבע, ופג תוקף כרטיס.

## תזכורות לחברים

התשתית בנויה במלואה (`src/services/notifications.ts`): תבניות הודעה, תור הודעות,
בחירת ערוץ לפי העדפת החבר, ומעקב אחר סטטוס ושגיאות.

ללא Integration פעיל ההודעות נשמרות בתור בסטטוס "בתור לשליחה" ואינן נשלחות בפועל.
חיבור ספק WhatsApp / SMS / Email בעתיד אינו מצריך שינוי בלוגיקה — רק מימוש
`NotificationProvider` ורישומו.

## הו"ק שוטפת מול מקום וריהוט

שני דברים שונים לחלוטין, ולכן שני מסכים נפרדים:

| | הוראת קבע שוטפת | מקום וריהוט |
| --- | --- | --- |
| מה זה | דמי חבר · חיוב חודשי קבוע | סכום שהחבר התחייב לו |
| סכום כולל | אין | יש (למשל 20,000 ₪) |
| יתרה | אין | יש, ויורדת עם כל תשלום |
| מתי נגמר | לא נגמר | כשההתחייבות שולמה במלואה |
| נשמר כ- | `standing_orders` בלבד | `commitments` + הוראת קבע מקושרת (אופציונלי) |

במסך המקומות מוצג לכל חבר: כמה התחייב, סכום התשלום החודשי, כמה תשלומים
מתוך כמה כבר שולמו, תאריך התשלום הראשון, יום החיוב, מועד החיוב הבא,
היתרה שנותרה, והעמותה שאליה משויכת ההתחייבות.

### כשהסכום הכולל אינו ידוע

אצל חלק מהחברים גובים סכום חודשי, אבל **כמה סוכם בסך הכל אינו רשום
בשום מקום** - ובפועל הוא שונה מאחד לשני: יש מי שהתחייב ל-10 תשלומים של
1,000 ₪ ויש מי שהתחייב ל-40 תשלומים של 500 ₪.

במקרה כזה ההתחייבות נרשמת **בלי סכום כולל**:

| מה שידוע | מה שאינו ידוע |
| --- | --- |
| התשלום החודשי | הסכום הכולל |
| כמה שולם עד היום | היתרה שנותרה |
| כמה תשלומים כבר בוצעו | כמה תשלומים נותרו |
| תאריך התשלום הראשון · יום החיוב · העמותה | המועד הצפוי לסיום |

מה שאינו ידוע מוצג כ**"לא ידוע"** ולא כמספר משוער. מספר משוער נראה
בדיוק כמו מספר אמיתי, ובמערכת כספית זו טעות שמתגלגלת הלאה: היא מנפחת
את סך ההתחייבויות, יוצרת יתרות שלא קיימות, ומסמנת חברים כמי שסיימו
לשלם כשהם באמצע.

ההוראה החודשית ממשיכה לחייב כרגיל, וכשהסכום האמיתי נודע מזינים אותו
במסך בלחיצה אחת. מאותו רגע היתרה מחושבת מהתשלומים שכבר בוצעו,
וההוראה תסתיים מאליה כשההתחייבות תסולק.

### שלוש דרכי תשלום

| דרך | מה קורה במערכת |
| --- | --- |
| **הוראת קבע** | נוצרת התחייבות + הוראה חודשית מקושרת. כל חיוב מקטין את היתרה, וההוראה מסתיימת מאליה כשההתחייבות סולקה. החיוב האחרון מוגבל לגובה היתרה ואינו חורג ממנה. |
| **שולם מראש** | נוצרת התחייבות ונרשם מיד תשלום מלא. ההכנסה נוצרת וקבלה מופקת לפי הגדרת העמותה. |
| **תשלומים ידניים** | נוצרת התחייבות עם יתרה מלאה. כל תשלום נרשם ידנית ומקטין את היתרה. |

מספר התשלומים והתשלום החודשי משלימים זה את זה - די למלא אחד מהם.

## תקציב

מסך התקציב מציג אומדן מול ביצוע. **האומדן אינו הוצאה**: הוא הערכה
שמוזנת ידנית, אינו יוצר שום רשומה כספית, ואינו נספר בסיכומי ההוצאות.
שתי העמודות מוצגות זו לצד זו כדי שההבדל יהיה גלוי.

- אומדן שנתי נפרס אוטומטית ל-12, כדי שאפשר יהיה להשוותו לחודשי.
- אומדן "לפי הצורך" אינו נפרס ואינו נכנס לסך החודשי.
- ההוצאה בפועל מחושבת כממוצע על פני 12 החודשים האחרונים, כדי שהוצאות
  עונתיות - חגים למשל - לא יעוותו את התמונה.

**עד לאן מגיע הכסף** מסכם את שורות התקציב לפי סדרן ומראה היכן ההכנסה
החודשית הצפויה נגמרת - מי מכוסה, מי מכוסה חלקית ומי לא מכוסה כלל.
ההכנסה הצפויה מחושבת מהוראות הקבע הפעילות בלבד (שוטפות + מקומות),
ואינה כוללת תרומות חד-פעמיות.

האומדנים הראשוניים הוזנו לפי רישום ההוצאות של הגבאי, ומסומנים ככאלה
בעמודת ההערה. כל אחד מהם ניתן לעריכה במסך, וערך שנערך ידנית לא נדרס
בעדכוני גרסה.

### צירוף חשבוניות

לכל הוצאה ניתן לצרף חשבונית (PDF או תמונה, עד 15MB). בעת רישום הוצאה
חדשה אפשר להעלות את החשבונית תחילה, והמערכת תנסה למלא מראש את הסכום,
התאריך ומספר החשבונית.

**החילוץ הוא הצעה בלבד וטעון אישור.** המימוש הנוכחי
(`src/integrations/invoices/heuristic.ts`) קורא טקסט גלוי בלבד ואינו מבצע
OCR: הוא מזהה סכום רק כשהוא מעוגן במילה כמו "סה"כ" או בסימן ₪, ומעדיף
להחזיר "לא ידוע" על פני ניחוש - בנתונים כספיים מספר שגוי גרוע ממספר חסר.
חשבונית סרוקה או PDF שבו העברית מקודדת לפי הגופן לא ייקראו.

חיבור שירות OCR אמיתי הוא מימוש של `InvoiceExtractionProvider`, בדיוק כמו
שאר הספקים במערכת.

## ייבוא חברי הקהילה

```bash
npm run import -- --reset
```

מייבא את הנתונים מ-`src/db/import-data/members.json`, שנוצר מקובץ האקסל
של הקהילה. לכל חבר נוצרים:

* **הו"ק שוטפת** - חיוב חודשי קבוע (דמי חבר), שרץ ללא הגבלת זמן.
* **התחייבות מקום/ריהוט** - סכום כולל, ולצדה הוראת קבע שמשלמת אותו
  בתשלומים. כל חיוב מקטין את יתרת ההתחייבות, וההוראה מסתיימת מאליה
  כשההתחייבות סולקה. כך רואים בבירור מי שילם הכול ומי באמצע.

המערכת מריצה את החיובים מתאריך ההתחלה של כל חבר ועד היום. כל חיוב נרשם
בתאריך שבו בוצע, ולכן הדוחות החודשיים וגיל החוב נכונים.

> **שימו לב:** קובץ האקסל כולל את סכום התשלום החודשי של המקום/ריהוט, אך
> לא את הסכום הכולל שהחבר התחייב לו. הייבוא גוזר אותו כ-20 תשלומים
> (`SEAT_INSTALMENTS` ב-`src/db/import.ts`). יש לעדכן את הערך, או לתקן כל
> התחייבות בנפרד במסך ההתחייבויות.

| דגל | משמעות |
| --- | --- |
| `--reset` | מחיקת הנתונים הקיימים ובנייה מחדש |
| `--members-only` | ייבוא החברים והוראות הקבע בלבד |

`--reset` מרוקן את הטבלאות מבפנים ואינו מוחק את קובץ בסיס הנתונים, ולכן
**אפשר לייבא גם כשהמערכת פועלת** - די ברענון הדפדפן כדי לראות את התוצאה.
מחיקת הקובץ עצמו הייתה נכשלת בחלונות, שם לא ניתן למחוק קובץ שתהליך אחר
מחזיק פתוח.

ללא `--members-only` נוספות גם התחייבויות להמחשה - עליות, תרומות, קידושים
ואירועים במצבי תשלום שונים - כדי שמסכי הגבייה והחובות לא יהיו ריקים.
**הן אינן מגיעות מקובץ האקסל**, וכולן מסומנות בהערה `[דוגמה]`:

```sql
DELETE FROM commitments WHERE notes LIKE '[דוגמה]%';
```
